# Grill Me: 計画・設計の質問攻めインタビュー

ユーザーの計画・設計・アイデアについて、**認識が揃うまで容赦なくインタビューする**。
決定木の各枝を下りながら、決定間の依存関係を一つずつ解消していく。
多くの失敗はコードが書けないからではなく、要件が最後まで具体化されていないことから起きる —— それをコミット前に潰すのが目的。

## 進め方

1. **対象の把握**: グリル対象（計画・設計・アイデア）を確認する。会話に既に出ていればそれを使い、無ければ何をグリルするか聞く。
2. **事実は自分で調べる**: 質問する前に、**環境（repos/ のコード・git 履歴・plans/・MCP のライブ状態）を調べれば分かる「事実」は自分で調べて済ませる**。ユーザーに聞くのは「決定」だけ。
3. **一問ずつ聞く**: AskUserQuestion で **1 回につき 1 問**。複数質問を同時に投げると混乱するので禁止。
   - 各質問には**自分の推奨回答を必ず添える**（AskUserQuestion では推奨案を先頭オプションにして「(推奨)」を付ける）。ギャップの指摘だけで終わらせず、埋め方まで示す。
   - 回答を受けてから次の質問へ。回答が新たな依存や矛盾を生んだら、その枝を先に掘る。
4. **決定木を網羅する**: スコープ・非ゴール・データ/状態・失敗モード・運用（誰が/いつ/壊れたらどうする）・セキュリティ・段階分け（今やる最小 vs issue 化する重い部分）など、各枝を漏れなく辿る。答えやすい順ではなく、**他の決定を左右する上流の決定から**聞く。
5. **合意まで実装しない**: ユーザーが「認識が揃った」と確認するまで、計画の実行・コード変更には着手しない。

## 締め

認識が揃ったら、決定事項を短くまとめて提示する:

- 決まったこと（決定と理由の一覧）
- 今やる最小スコープ / issue 化して先送りする重い部分（おうち運用の原則に従う）
- 未解決のまま意図的に残した点

必要なら、まとめを元に issue 起票（github-projects MCP）や plans/ への設計メモ化を提案する（実施はユーザー確認後）。

## 注意

- このスキルは**インタビューが本体**。勝手に調査レポートや実装に脱線しない。
- 質問は具体的に。「エラーハンドリングはどうしますか？」ではなく「X が落ちたとき Y のデータは失われますが、リトライで拾いますか、捨てて次周期に任せますか？（推奨: 捨てる。理由: …）」の形。
- ユーザーの回答に迎合しない。矛盾・楽観・未定義を見つけたら遠慮なく突く。
